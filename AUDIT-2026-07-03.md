## S — Sécurité (gravité décroissante)

### S1 — supabase-js chargé depuis CDN sans SRI ni version épinglée
- **Fichier** : `index.html:165`.
- **Constat** : `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/...`
  est en version flottante (`@2`) et **sans attribut `integrity`**, alors
  que Leaflet, lui, est épinglé + SRI. La CSP autorise `cdn.jsdelivr.net`
  en `script-src` : un CDN compromis ou une version malveillante publie du
  JS qui manipule les jetons de session (supply chain → XSS complet).
  Le commentaire de `middleware.js:21` (« SRI côté front ») est donc faux
  pour supabase-js.
- **Correctif** : épingler une version exacte (`@supabase/supabase-js@2.x.y`)
  + hash SRI `sha384`, `crossorigin="anonymous"`. Alternative durable :
  servir le bundle en local (`js/vendor/`), retirer jsdelivr de la CSP.
- **Test de fermeture** : altérer le hash → le script doit être bloqué
  (console CSP/SRI) ; avec le bon hash, connexion magic link OK.
- **Statut** : ✅ corrigé+commit `04d95e4` — bundle **auto-hébergé**
  `js/vendor/supabase.min.js` (v2.110.0, tiré du registre npm),
  `cdn.jsdelivr.net` retiré du `script-src` (plus aucun CDN pour ce
  script) ; `node --check` OK, parcours navigateur à rejouer avec la
  refonte v2.

### S2 — `set_updated_at` : `search_path` mutable (lint advisor)
- **Fichier** : `supabase/migrations/0001_init.sql:9` (fonction déployée).
- **Constat** : vérifié en base : `proconfig` vide → `search_path`
  MUTABLE. Lint sécurité Supabase `function_search_path_mutable` :
  une fonction `security definer`/trigger résolvant des objets non
  qualifiés peut être détournée via un schéma attaquant.
  Exploitabilité faible ici (fonction triviale, `now()` = pg_catalog),
  mais c'est LE lint advisor standard et le correctif est trivial.
- **Correctif** : migration `0002` :
  `alter function public.set_updated_at() set search_path = '';`
- **Test de fermeture** : `select proconfig from pg_proc where proname =
  'set_updated_at'` → contient `search_path=` ; UPDATE d'un nœud → 
  `updated_at` toujours rafraîchi.
- **Statut** : ✅ corrigé+commit — migration
  `0002_advisors_search_path_rls_initplan.sql` **appliquée** (go Paul
  2026-07-03) ; vérifié en base : `proconfig = search_path=""`.

### S3 — Inscription ouverte à tous via magic link (décision produit)
- **Fichier** : `js/app.js:533` (`signInWithOtp`).
- **Constat** : `shouldCreateUser` vaut `true` par défaut : toute adresse
  e-mail peut créer un compte et stocker des données dans la base
  (abus, coût, surface de spam). La RLS isole les données, mais l'accès
  n'est pas restreint au réseau de Paul.
- **Correctif** : `options: { shouldCreateUser: false }` + création des
  comptes autorisés à la main (dashboard) ou table d'invitations.
  **Touche l'auth → gate Paul.**
- **Test de fermeture** : magic link sur une adresse inconnue → erreur
  générique, aucun compte créé.
- **Statut** : ✅ décision Paul 2026-07-03 (« je dois être le seul ») —
  `shouldCreateUser: false` posé dans `js/app.js` (mono-utilisateur).
  ⏭ Restent 2 actions dashboard (hors MCP) : ① inviter le compte de Paul
  (Authentication → Users → Invite — la base compte 0 utilisateur : sans
  ça, aucune connexion possible) ; ② désactiver « Allow new signups »
  (défense côté serveur, le flag client ne suffit pas seul).

### S4 — CSP `connect-src https://*.supabase.co` trop large
- **Fichier** : `middleware.js:27`.
- **Constat** : le wildcard autorise des appels vers **n'importe quel**
  projet Supabase. En cas d'XSS résiduel, il offre un canal
  d'exfiltration « propre » vers une instance attaquant.
- **Correctif** : remplacer par l'hôte du projet
  (`https://leosfqyidgsaescjbfom.supabase.co`), via env
  (`SUPABASE_URL`) lue dans le middleware pour éviter le hard-code.
- **Test de fermeture** : `fetch` vers un autre `*.supabase.co` depuis la
  console → bloqué par la CSP ; appels applicatifs OK.
- **Statut** : ✅ corrigé+commit `04d95e4` (go global Paul) — `connect-src`
  restreint à l'origine de `SUPABASE_URL` (env), repli wildcard si env
  absente en local.

### S5 — Rate-limit : IP dérivée de `x-forwarded-for` (spoofable hors Vercel)
- **Fichier** : `middleware.js:44-48`.
- **Constat** : `clientIp()` prend le premier élément de
  `x-forwarded-for`. Vercel réécrit normalement cet en-tête en
  production, mais le code ne doit pas en dépendre silencieusement :
  derrière tout autre front (ou en local), l'en-tête est forgeable →
  contournement du rate-limit par rotation d'IP fictives (et pollution
  mémoire de la `Map`).
- **Correctif** : préférer `x-real-ip` (posé par Vercel) puis retomber
  sur `x-forwarded-for` ; documenter l'hypothèse « déployé sur Vercel ».
- **Test de fermeture** : en preview Vercel, 61 requêtes avec
  `x-forwarded-for` forgé aléatoire → la 61ᵉ reçoit quand même 429.
- **Statut** : ✅ corrigé+commit `4d3877f` (go global Paul) — `x-real-ip`
  prioritaire, hypothèse Vercel documentée dans le code ; test 61 req en
  preview à rejouer au déploiement.

### S6 — Paramètres Auth non audités (advisors inaccessibles)
- **Constat** : les lints « leaked password protection », « OTP expiry »

- **Correctif** : passer les advisors *security* + *performance* depuis le

### P1 — Policies RLS : `auth.uid()` réévalué par ligne
- **Fichier** : `supabase/migrations/0001_init.sql:72-95` (8 policies).

  `owner_id = auth.uid()` nu. Lint perf Supabase `auth_rls_initplan` :

- **Statut** : ✅ corrigé+commit — même migration `0002` que S2,
  appliquée ; vérifié : les 8 policies affichent `( SELECT auth.uid() )`.

## U — UX & corrections (impact × effort décroissant)

### U1 — Création de nœud sans e-mail impossible en mode connecté (400)
- **Fichiers** : `js/app.js:400` (envoie `email: ''`) ×
  `api/_lib/validate.js:92-99` (`EMAIL_RE.test('')` → « Email invalide »).
- **Constat** : le formulaire envoie les champs optionnels vides en `''`.
  L'API rejette `''` comme e-mail invalide → **toute création/édition de
  nœud sans e-mail échoue en 400** en mode connecté. Bloque le flux
  principal (les chantiers du jeu de démo n'ont pas d'e-mail…).
  Non visible en mode démo (pas d'appel API).
- **Correctif** (défense des deux côtés, 1 commit) : front — omettre les
  champs optionnels vides du payload ; API — normaliser `'' → null` pour
  `email`/`telephone`/`ville`/`adresse`/`notes` avant validation.
- **Test de fermeture** : création d'un nœud « chantier » sans e-mail ni
  téléphone en mode connecté → 200, fiche affichée.
- **Statut** : ⏳ ouvert — premier patch P3 proposé.

### U2 — Saisie manuelle de lat/lng obligatoire pour créer un nœud
- **Fichiers** : `index.html:116-125`, `js/app.js:387-392`.
- **Constat** : personne ne connaît les coordonnées GPS d'un artisan.
  C'est LE point de friction n°1 du produit.
- **Correctif** (2 temps) : (a) mode « placer sur la carte » : au clic
  dans le formulaire, un clic carte remplit lat/lng (aucune dépendance) ;
  (b) géocodage d'adresse Nominatim/OSM (politique d'usage : 1 req/s,
  User-Agent identifiant) — déjà au cap de ROADMAP-SITE, appel externe →
  timeout + décision Paul.
- **Test de fermeture** : créer un nœud en cliquant sur la carte, sans
  taper de coordonnées.
- **Statut** : ⏳ (a) ouvert — patch P3 sans dépendance ; ⏭ (b)
  géocodage reporté — appel externe, décision Paul.

### U3 — Pas d'anti double-soumission ni d'état de chargement
- **Fichiers** : `js/app.js:385-418, 446-466`.
- **Constat** : les boutons restent actifs pendant l'appel API : un
  double-clic crée deux nœuds/relations ; aucun retour visuel d'attente.
- **Correctif** : désactiver le bouton submit pendant l'appel
  (`disabled` + libellé « Enregistrement… »), réactiver en `finally`.
- **Test de fermeture** : double-clic rapide sur « Enregistrer » → un
  seul nœud créé.
- **Statut** : ⏳ ouvert — patch P3.

### U4 — Mode connecté sans session : carte vide, aucun message
- **Fichier** : `js/app.js:117-122`.
- **Constat** : config Supabase présente + non connecté → la carte est
  simplement vide, sans invitation à se connecter (l'utilisateur croit à
  un bug).
- **Correctif** : état vide explicite : bandeau « Connectez-vous pour
  voir votre réseau » (réutiliser `#bandeau-demo` avec un libellé dédié).
- **Test de fermeture** : ouvrir le site configuré, déconnecté → message
  visible ; après connexion → données affichées, message masqué.
- **Statut** : ⏳ ouvert — patch P3.

### U5 — PATCH d'un nœud inexistant → 500 au lieu de 404
- **Fichier** : `api/reseau/nodes.js:59-67` (`.single()`).
- **Constat** : `.single()` échoue (`PGRST116`) quand l'id n'existe pas /
  n'appartient pas à l'utilisateur → mappé en 500 « Erreur interne »
  (faux signal d'erreur serveur, logs pollués). DELETE utilise déjà
  `.maybeSingle()`, PATCH non.
- **Correctif** : `.maybeSingle()` sur le PATCH (le `if (!data) → 404`
  existe déjà juste dessous).
- **Test de fermeture** : PATCH avec un UUID aléatoire → 404
  « Nœud introuvable ».
- **Statut** : ⏳ ouvert — patch P3 trivial (1 ligne).

### U6 — Limites de saisie front ≠ contrat API
- **Fichiers** : `index.html:102,106` (ville 120, adresse 250) vs

- **Constat** : incohérence silencieuse — sans gravité aujourd'hui, mais

- **Correctif** : aligner les `maxlength` HTML sur le contrat (200/500).
- **Test de fermeture** : saisir 300 caractères d'adresse → accepté et
  sauvegardé.
- **Statut** : ⏳ ouvert — patch P3.

### U7 — `invaliderTaille()` jamais branchée (tuiles mal rendues)
- **Fichiers** : `js/carte.js:105-107` (exposée), `js/app.js` (jamais

- **Constat** : Leaflet doit recalculer sa taille quand la mise en page

- **Correctif** : appeler `UltimaCarte.invaliderTaille()` sur

- **Test de fermeture** : redimensionner la fenêtre / pivoter le mobile →
  carte complète, pas de bandes grises.
- **Statut** : ⏳ ouvert — patch P3.

### U8 — Fiche : direction des relations non indiquée
- **Fichier** : `js/app.js:294-309`.

- **Correctif** : préfixer « → vers X » / « ← de X » selon le sens.
- **Test de fermeture** : fiche d'un nœud source ET d'un nœud cible →

- **Statut** : ⏳ ouvert — patch P3.
